# Orb reference and official Computer Use: desktop integration assessment

Checked 2026-09-27 against the official tag [`dsh-v0.1.7-rc.2`](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.7-rc.2) and the reference project's `main` at `72f1d738458a223696685a909e806b683eff5885`. The local community checkout's Computer Use service and provider files have no committed diff from the official tag. The reference checkout is at `../../reference/deepseek-harness-orb`.

## Reference project architecture

- This is a full Harness fork, not a standalone orb component. Its [README](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/README.md) targets macOS and Windows and describes an orb chat for foreground work plus delegated background Code Agent sessions; Linux orb support is absent. The [desktop manifest](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/apps/desktop/package.json) uses Electron 44, TypeScript 6, electron-builder 26, `koffi` for Windows native calls, and `ws`; the broader web client uses React/Cordis. The floating shell is plain [HTML/CSS/JavaScript](https://github.com/mini-yifan/deepseek-harness-orb/tree/72f1d738458a223696685a909e806b683eff5885/apps/desktop/renderer), while its compact chat content is a [React UI plugin](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/packages/client/ui-overlay-chat/src/client/index.ts) embedded through a local `dsh-app://` iframe.
- The [floating-window controller](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/apps/desktop/src/floating-window.ts#L620-L685) creates a frameless, transparent, always-on-top `BrowserWindow` with Electron sandboxing and context isolation. It handles right-edge positioning, dragging, dock animation, compact/expanded geometry, and screen changes. Its [overlay guard](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/apps/desktop/src/floating-window.ts#L859-L961) temporarily hides the orb from Windows capture and makes it click-through during HID actions, then resets state on host exit. macOS capture separately excludes orb window IDs.
- The renderer starts and prompts a dedicated Session over restricted RPC ([renderer](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/apps/desktop/renderer/floating.js#L610-L749), [desktop IPC](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/apps/desktop/src/main.ts)); the desktop persists the orb session under its Profile in [`floating-session.json`](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/apps/desktop/src/floating-session.ts). The visible chat is not an independent agent runtime: it retains that Harness Session using the UI plugin.

## Author's Computer Use versus the official providers

- The orb fork has its own [experimental Computer Use plugin](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/packages/experimental/tool-computer-use/src/plugin.ts): a fixed set of GUI tools for clicks, text entry, scrolling, hotkeys, drag, waits, screenshots, and opening/listing apps. It injects a first-turn frontmost-window screenshot and returns a fresh screenshot after each GUI action. The [policy](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/packages/experimental/tool-computer-use/src/policy.ts) is explicitly frontmost-window-centric. This is an agent preset and tools implementation, not an implementation of the official `dsh-computer-use` provider interface.
- The fork directly owns OS automation: [macOS backend](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/packages/experimental/tool-computer-use/src/macos.ts) uses ScreenCaptureKit, CGEvent/JXA, and application/clipboard integration; [Windows backend](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/packages/experimental/tool-computer-use/src/windows-native.ts) uses `koffi` with Win32 capture and `SendInput`. The package's [README](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/packages/experimental/tool-computer-use/README.md) documents these platform and permission boundaries. Linux execution is unsupported.
- In contrast, official Computer Use registers **one** provider and delegates actual desktop control either to an external `cua-driver mcp` process or to the `@trycua/cua-driver` native SDK loaded in the host; tool sets are driver-defined rather than the fork's fixed schema. The fork's internal [architecture note](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/.agents/notes/implemented/architecture/2026-09-24-orb-on-dsh-0.1.7.md) explicitly keeps official Computer Use providers out of the same orb Profile and defers moving its backend onto the official provider seam. Installing both into one Profile risks competing desktop controllers and tool/policy ambiguity.
- Security policy differs materially. The fork's [permission state](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/apps/desktop/src/orb-permission.ts#L7-L41) defaults to `danger-full-access`; its [background Code Agent delegation](https://github.com/mini-yifan/deepseek-harness-orb/blob/72f1d738458a223696685a909e806b683eff5885/packages/experimental/tool-computer-use/src/code-agent-unattended.ts#L56-L70) auto-answers approval and user-question requests for that delegated session. This is not a suitable default to copy into the community desktop. The official provider packages do not themselves define per-action approval; an integrating app must supply a coherent policy above them.

## Integration risks and recommended sequence

1. **Start with UI-only orb.** Reuse the ideas of a sandboxed transparent Electron window, restricted IPC, and retained Harness Session, but connect it to the community desktop's existing process manager, Profile/data-directory switching, quick restart, diagnostics, and NAS authority. A UI-only orb should not install or enable Computer Use automatically. Persist orb state per data directory and prevent a stale orb from sending to a different Profile after switching.
2. **Make lifecycle and focus explicit.** Test drag/dock across displays, DPI and work-area changes, full-screen apps, accessibility/reduced motion, window focus, screen-sharing privacy, capture exclusion, and reliable restoration from click-through after failed/cancelled operations. The orb must not show an old screenshot as if it were live or take input while the underlying target changes.
3. **Add optional control only through one selected backend.** Prefer the existing official Cua Driver MCP/native settings and capabilities when adding GUI control; do not install the fork's tool package in parallel by default. Build an orb-to-Session admission policy, explicit enablement and OS-grant explanation, a desktop-level observe–act–verify scheduler, and local-only/NAS rules. Keep current high-risk approval behavior; never import the fork's full-access default or unattended approval listener.
4. **Defer advanced fork features.** Selection toolbar, observation ribbon, automatic screenshots, delegated background Code Agent, and custom macOS/Windows native capture are separate product/security projects. The reference does not provide Linux parity. Windows/macOS installed-build tests (not just development mode) are required before shipping a floating overlay.

This was a static source review, not a runtime or native-install validation of the reference project. Its exact commit is recorded above so these claims remain reproducible.

## What the official implementation provides

- [`dsh-computer-use`](../packages/computer-use/computer-use/src/index.ts#L15-L45) is an exclusive **provider registration**, not a desktop controller. It stores one provider name and rejects a second registration, even one with the same name. The [official subsystem contract](../docs/subsystems/computer-use.md#choose-a-provider) says it has no shared click/screenshot methods or model-controlled provider selector.
- The [MCP provider](../packages/experimental/computer-use-cua-driver-mcp/src/index.ts#L52-L71) starts an already-installed `cua-driver mcp` executable over stdio through the existing MCP client. Its [README](../packages/experimental/computer-use-cua-driver-mcp/README.md#use-this-package) places driver installation and desktop permissions with Cua Driver; it publishes the driver's discovered tools as `mcp__cua-driver-mcp__*`, not a DSH-defined action API. Initialization failure rolls back its registration, while reconnect keeps it reserved.
- The [native provider](../packages/experimental/computer-use-cua-driver-native/src/index.ts#L50-L137) imports the pinned `@trycua/cua-driver` npm SDK (`0.28.0` in its [manifest](../packages/experimental/computer-use-cua-driver-native/package.json#L37-L42)), creates the runtime in the host process, validates the discovered catalog, and publishes `cua_driver_native__*` tools. It aborts outstanding calls and waits for shutdown on unload. Its [README](../packages/experimental/computer-use-cua-driver-native/README.md#host-requirements) says OS desktop grants belong to the launching host and warns that a native crash can terminate that process.
- The native provider's [model guidance](../packages/experimental/computer-use-cua-driver-native/src/index.ts#L37-L41) asks for fresh window snapshots, recommends background delivery, and requires verification after an action. Element tokens become stale after a new snapshot. Cancellation does not undo input already sent. This is model guidance, not a transactional desktop-operation guarantee.
- Both providers use the normal tool pipeline. The [MCP result adapter](../packages/mcp/mcp-client/src/tools.ts#L225-L312) retains canonical results and projects screenshots to durable attachments only after it verifies an attachment store and an image-capable model route ([admission check](../packages/mcp/mcp-client/src/tools.ts#L346-L439)). Otherwise the model receives an image-unavailable diagnostic; raw result data can still be available to programmatic callers.

## Security and concurrency boundary

The official [subsystem documentation](../docs/subsystems/computer-use.md#lifetime-and-desktop-sharing) states that the sole registered provider does **not** reserve a desktop per Session. Separate Sessions and DSH processes can interleave observation and actions, so callers must coordinate complete observe–act–verify workflows. The provider READMEs describe explicit activation and OS permissions, but no dedicated desktop permission UI or per-action approval implemented by these provider packages ([MCP limitations](../packages/experimental/computer-use-cua-driver-mcp/README.md#known-limitations-and-deferred-work), [native host requirements](../packages/experimental/computer-use-cua-driver-native/README.md#host-requirements)). This does not establish what higher-level application approval policy does; it only identifies the provider's own boundary.

## Implications for an orb (inference)

An orb is a separate desktop **presentation and control surface**, not another Cua Driver provider. Its always-on-top window, drag and edge-snap behavior, display/DPI transitions, click-through state, focus handling, visibility while screen capture runs, and lifecycle with the main window must be designed in Electron or another desktop UI layer; the official Computer Use service supplies none of these ([service source](../packages/computer-use/computer-use/src/index.ts#L15-L45)). If the orb shows live screenshots or starts Agent actions, it needs an explicit bridge and privacy/permission policy, rather than reading model attachments as if they were a live screen feed ([result adapter](../packages/mcp/mcp-client/src/tools.ts#L346-L439)). If it exposes control of the desktop, serialize or otherwise coordinate observe–act–verify across Sessions and processes and re-check targets after cancellation, because provider registration is not a workflow lock ([subsystem contract](../docs/subsystems/computer-use.md#lifetime-and-desktop-sharing), [native guidance](../packages/experimental/computer-use-cua-driver-native/src/index.ts#L37-L41)).

For the community Desktop, the native provider reuses the app process's OS grants but adds crash coupling; the MCP provider isolates driver execution and can own its own grants, at the cost of an external executable and connection lifecycle ([native README](../packages/experimental/computer-use-cua-driver-native/README.md#host-requirements), [MCP README](../packages/experimental/computer-use-cua-driver-mcp/README.md#use-this-package)). This is a trade-off for an orb-triggered computer-control feature, not a reason to couple basic orb rendering to either provider.
