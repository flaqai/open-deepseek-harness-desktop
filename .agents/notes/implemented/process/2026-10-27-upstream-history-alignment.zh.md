# Agent Note: 上游祖先关系与功能集成

Status: implemented

[English](2026-10-27-upstream-history-alignment.md) | 中文

## 问题

GitHub 比较 fork 的默认分支与上游 master，而社区发行版集成固定的官方标签。只推送发行或修复分支会使默认分支的比较状态滞后。记录祖先关系而不导入源码，还会改变 Git 推断的合并基线，使后续普通合并遗漏尚未集成的功能变化。

## 决策

[集成记录](../../../upstream-integration.json) 区分已审阅的官方标签与仅确认历史关系的上游 master 提交。后者由精确 `mergeSubject` 找到的合并提交及其指定序号的父提交确定，不使用会移动的上游引用作为固定基线。真实功能基线只在源码集成和验证完成后推进。经用户授权的历史对齐采用 `ours` 合并，并核对该次合并前后 tree ID 完全一致；它只改变祖先关系，不表示已集成功能。

大版本上游更新推送时，获取两个远端，用 `git rev-list --left-right --count` 比较 `origin/master...upstream/master`，检查缺少的提交，再选择内容集成或经授权的历史对齐。推送 master 后重新读取远端 SHA 并再次比较。分别报告剩余落后数与真实功能基线；只推送发行分支不算完成这项检查。

这些推送前后都要用 `git worktree list --porcelain` 列出工作树。保留主工作区，以及仍有活跃任务、未提交或未跟踪内容、或尚未合入 master 的提交的工作树。无用的集成工作树只有在完整状态干净、其末端提交是 master 的祖先、且已检查忽略文件中是否有需保留的产物或本地数据后才可移除。对准确路径执行 `git worktree remove`；若属于应用管理并已附加的工作树，则通过应用工具归档。保留分支引用，不强制移除，并分别报告移除和保留的工作树。仅请求清理不代表授权推送。

历史对齐超过真实功能基线时，下次源码集成要解析 `functionalBaseline.ref`，比较从该提交到固定目标的完整差异。Git 自动选择的合并基线不足以覆盖这些变化。显式基线命令 `git merge-tree --write-tree --merge-base=<functional-baseline> HEAD <target>` 会保留此前跳过的增量以供冲突审阅。集成记录与最终源码改动一起更新。

## 考虑过的替代方案

**自动合入最新上游内容来清零计数。** 不采用，因为此次祖先关系修复要求保留社区源码，并未授权采用未经审阅的上游功能。

**只记录祖先关系，不保留真实功能基线。** 不采用，因为后续合并可能悄悄遗漏仅确认了历史关系的变化。

## 影响

落后数为零只说明祖先关系，不表示功能完全一致。历史对齐之后，下次上游集成需要显式指定功能审阅基线。tree ID 核验只覆盖这次历史合并，不覆盖同次推送中此前有意完成的修复。已发布标签和产物保持不变。
